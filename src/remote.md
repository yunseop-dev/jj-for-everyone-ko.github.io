# 커밋을 원격으로 보내기

````admonish reset title="진행 상황 초기화" collapsible=true
이 장의 시작으로 되돌리려면 다음 명령을 실행하세요.

```sh
curl https://jj-for-everyone.github.io/reset.sh | bash -s remote
cd ~/jj-tutorial/repo
```
````

잃고 싶지 않은 커밋이 생겼습니다.
하지만 지금 방식대로라면 백업이 전혀 없습니다.
`~/jj-tutorial/repo` 디렉터리를 삭제하면 어떻게 될까요?
`.git`, `.jj` 디렉터리도 함께 사라집니다.
버전 관리 데이터베이스 전체가 그 안에 저장되어 있으니, 작업물을 복구할 수 없게 됩니다!

이 문제는 커밋을 다른 위치에 복제해 두면 해결됩니다. 이를 **원격(remote)** 이라고 부릅니다.
원격으로 커밋을 보내면 백업이 될 뿐 아니라, 협업을 위해 작업 내용을 공유하기도 쉬워집니다.

가장 일반적인 원격 형태는 [GitHub](https://github.com/) 같은 온라인 서비스에 저장소를 호스팅하는 것입니다.
하지만 계정이 필요하고 약간의 설정도 있어야 하므로, 이 튜토리얼에서는 더 간단한 방법을 사용합니다.
원격을 컴퓨터의 다른 위치에 있는 새 디렉터리에 저장할 것입니다.
이 방식은 백업이나 협업 측면에서는 별로지만, 원격이 어떻게 동작하는지 배우기에는 딱 좋습니다.
GitHub 사용과 관련된 실용 팁은 [다음 장](github.md)에서 다룹니다.

## 원격 초기화

다음 명령은 원격으로 사용할 새 저장소를 초기화합니다.

```sh
git init --bare -b main ~/jj-tutorial/remote
```

실제로는 다른 형태의 원격을 사용하게 될 가능성이 높으므로, 여기에서 세부 내용을 이해하지 않아도 됩니다.
그래도 궁금하다면 아래 상자를 펼쳐 보세요.

````admonish note title="원격(베어) 저장소와 일반 저장소의 차이" collapsible=true
`git init --bare`는 우리의 주 저장소를 만들 때 사용한 `jj git init`과 매우 비슷합니다.
하지만 "일반" Jujutsu 저장소 대신 "베어" Git 저장소를 만듭니다.

무엇이 다를까요?

일반 Jujutsu 저장소는 두 부분으로 이루어져 있다고 생각해 보세요.
(1) `.git`, `.jj` 디렉터리에 저장된 내부 데이터베이스와 (2) 수정 가능한 실제 프로젝트 파일, 즉 **워킹 카피**입니다.
"카피"라는 말이 핵심입니다. 파일은 내부 데이터베이스에도 저장되어 있기 때문입니다.
데이터베이스 밖에 파일 사본이 존재하는 이유는 읽고 수정, 즉 "작업"하기 위함입니다.
그래서 "워킹 카피"라는 이름이 잘 어울립니다.

베어 저장소는 **워킹 카피가 없는** Git 저장소이며 Jujutsu 고유 메타데이터도 없습니다.
우리는 베어 저장소를 오직 커밋을 주고받는 용도로만 사용할 것이므로 워킹 카피나 `.jj` 디렉터리가 필요 없습니다.

새 베어 저장소 내용을 살펴보면, 주 저장소의 `.git` 디렉터리와 구조가 매우 비슷합니다.
```
ls -lah ~/jj-tutorial/repo/.git
ls -lah ~/jj-tutorial/remote
```

`-b main` 옵션은 기본 브랜치 이름을 "main"으로 지정합니다.
지정하지 않으면 설치 환경이나 설정에 따라 기본 브랜치 이름이 달라질 수 있고, 그러면 나중에 문제가 됩니다.
````

## 원격 연결

저장소는 특정 이름 아래 원격의 위치를 저장함으로써 원격과 연결됩니다.
원격 이름은 아무거나 지정할 수 있지만, 하나만 있을 때는 **origin**이라는 이름을 쓰는 것이 관례입니다.

```sh
jj git remote add origin ~/jj-tutorial/remote
```

여기서는 파일 시스템 경로로 원격을 연결했습니다.
GitHub 같은 서비스에 있는 저장소를 사용할 때는 경로 대신 URL을 지정합니다.
자세한 내용은 나중에 다룹니다.
모든 것이 잘 되었다면 다음 명령으로 원격 목록에 `origin`이 표시되어야 합니다.

```sh
jj git remote list
```

## 북마크 추가

원격으로 작업을 보내기 전에 넘어야 할 장애물이 하나 더 있습니다.
원격 저장소는 정말 많은 커밋을 받으며, 그중 일부는 결국 필요 없어집니다.
그래서 필요 없는 커밋은 자동으로 삭제할 수 있으면 좋습니다.
그렇다면 어떤 커밋을 삭제하고 어떤 커밋을 남겨야 하는지 원격은 어떻게 알까요?
바로 북마크 덕분입니다!

북마크는 커밋에 붙이는 간단한 이름표입니다.
북마크가 붙은 커밋은 중요하다고 간주되어 자동으로 삭제되지 않습니다.
이 메커니즘 때문에 원격으로 커밋을 보내려면 북마크가 **필수** 입니다.

완료한 커밋을 가리키도록 **main**이라는 북마크를 만들어 봅시다.
"main"은 프로젝트의 주요 상태를 나타내는 관례적인 이름입니다.
과거에는 "master"라는 이름도 널리 사용되었습니다.

```sh
jj bookmark create main --revision mkmqlnox # <- 여기에는 자신의 change ID를 넣으세요
```

`jj bookmark create` 명령은 이름(`main`)과, 북마크가 가리킬 커밋을 요구합니다.
커밋은 change ID(`--revision mkmqlnox`)로 지정합니다.
우리 맥락에서 "revision"과 "commit"은 동의어입니다.
`--revision` 플래그는 `-r`로 줄일 수 있습니다.
`jj log`로 결과를 확인해 봅시다.

## 북마크 추적

지금은 원격으로 커밋을 보내고 싶어서 북마크를 배우고 있습니다.
하지만 북마크는 로컬 전용 용도로도 사용할 수 있습니다.
예를 들어 기억하기 쉬운 이름으로 북마크를 만들어 특정 커밋을 가리키게 할 수 있습니다.
따라서 모든 북마크를 원격으로 보내고 싶지는 않을 수도 있습니다.

Jujutsu는 원격으로 보내야 할 북마크를 "추적 중" 상태로 표시해 구분합니다.
`main` 북마크를 원격으로 보내려면 먼저 "추적"해야 합니다.

```sh
jj bookmark track main@origin
```

`@origin`은 `main`을 `origin`이라는 원격으로 보내겠다는 뜻입니다.
여러 개의 원격이 있고 특정 원격에만 북마크를 보내고 싶을 때 필요한 정보이지만, 지금은 크게 신경 쓰지 않아도 됩니다.

## 북마크 푸시

이제 연결도 되었고, 북마크도 만들었으니 커밋을 원격으로 보내 봅시다.
커밋을 보내는 기술 용어는 "푸시(push)"입니다.
"원격으로 푸시하다", "GitHub로 푸시하다" 같은 표현을 자주 듣게 될 겁니다.
특정 북마크를 푸시하는 명령은 다음과 같습니다.

```sh
jj git push --bookmark main
```
